## วิธีอ่านผล

- **Display:** จากคลิกจน DOM เป้าหมายมองเห็น แล้วรอสอง animation frames เป็นตัวแทนโอกาสที่จอได้วาดภาพ ไม่ใช่เวลาจากภาพหน้าจอ
- **Data:** ข้อมูลหรือปุ่มที่หน้านั้นต้องใช้พร้อม สำหรับ Simulation รอฉากวาดเฟรมแรกด้วย
- **Ready:** หลัง Data แล้วรอรูปที่เกี่ยวข้องใน viewport, รูปที่ไม่ได้ lazy-load, ฟอนต์ และรูปพื้นหลัง decode เสร็จ รูป lazy ที่อยู่นอกจอแยกนับไว้
- รายงานใช้ค่ามัธยฐาน `[ต่ำสุด–สูงสุด]` ไม่คำนวณ p95 จากตัวอย่างเพียง 3 ครั้ง ข้อมูลที่หายคงเป็น missing ไม่แปลงเป็นศูนย์

Chrome แบบ headless ใช้จอ 1366×900, motion ปกติ, ไม่มีการจำกัด CPU/เครือข่าย แต่ละ sample เปิด browser context ใหม่ การดักคำขอเพื่อใช้ข้อมูลจำลองทำให้ HTTP cache ปิดอยู่ การกลับเข้าหน้าเดิมยังใช้ JavaScript module ที่โหลดไว้ในหน่วยความจำ สลับลำดับก่อน/หลังในแต่ละรอบเพื่อลดผลจากการรันรุ่นใดรุ่นหนึ่งก่อนเสมอ

### ผลบริการจริงหลังใช้ endpoint ใหม่

ผู้ใช้ยืนยันว่าอัปเดตแล้วและ `inspectSetup` ผ่าน รอบแรกเว็บยังเรียก URL เดิม พบครู Login 3 calls และโหลดห้อง 2 calls ทั้งสามรอบ จึงไม่ผ่านเงื่อนไขเผยแพร่ แม้ใช้งานได้ครบ 6 journeys เก็บผลนี้ใน `tmp/apps-script-update-20261025/live-after.json` และ `live-attempt-1-gate.json` โดยไม่นับเป็นผลของ backend ใหม่ จากนั้นผู้ใช้ส่ง `/exec` อีก URL จึงเปลี่ยน `assets/integrations/sheets-config.js` และสร้าง snapshot ใหม่ ตรวจ 975 ไฟล์พบว่าต่างจาก snapshot ก่อนหน้าเฉพาะ config นี้

## งานต่อ: ใช้ข้อมูลผิวใบซ้ำเมื่อกลับเข้าฉาก

`plant-growth-leaf-surface.js` เก็บข้อมูล pixels ของผิวใบทั้งสามแผนที่หลังคำนวณครั้งแรก แล้วทำสำเนาข้อมูลและสร้าง `DataTexture` ใหม่ให้แต่ละฉากเมื่อกลับเข้า บัฟเฟอร์และทรัพยากร GPU ของแต่ละฉากจึงยังแยกกัน สูตรสร้าง pixels สี รายละเอียดผิว geometry และสูตรทดลองไม่เปลี่ยน แลกกับ RAM ที่เก็บ cache ไว้ **3 MiB ต่อแท็บหลังเปิดฉากต้นไม้** นอกเหนือจากข้อมูล 3 MiB ของฉากที่กำลังใช้และ texture บน GPU; cache หายเมื่อโหลดหน้าใหม่หรือปิดแท็บ

วัดซ้ำด้วย `navigation-performance.mjs` ที่ไม่แทรกตัวจับเวลาในไฟล์โมเดล ใช้เส้นทางนักเรียนก่อน/หลังอย่างละ 3 ครั้ง รวม **6 journeys ผ่านทั้งหมด** ไม่มี page/network error, blocked writes หรือ cleanup failures:

| ขั้นตอนในชุด navigation | Ready ก่อน cache มัธยฐาน [ต่ำสุด–สูงสุด] ms | Ready หลัง cache มัธยฐาน [ต่ำสุด–สูงสุด] ms |
| --- | ---: | ---: |
| เข้า Simulation ครั้งแรก | 2,200.1 [1,758.0–5,448.1] | 1,695.2 [1,671.3–1,774.8] |

การกลับเข้าฉากลดลง 136.4 ms ที่มัธยฐานของชุดนี้ ส่วนเวลารวมครั้งแรกแม้ต่ำลงในชุด navigation แต่ range ทับซ้อนกันและผล diagnostic ไม่ได้แสดงการลดงานคำนวณครั้งแรก จึงยังไม่สรุปว่า cache ทำให้การเข้าครั้งแรกเร็วขึ้น รายงานดิบ: `tmp/performance-leaf-cache-20261025/navigation.json`; ตารางเต็ม: `navigation-summary.md` และ `.json` ในโฟลเดอร์เดียวกัน

ตรวจประกอบงานต่อผ่าน **29 tests**: cache 5, ตัววัด startup 5, เครื่องมือ performance เดิม 10, bundler 5 และ regression สูตร/พืช/native models/simulation อีก 4 ไฟล์ การตรวจ cache เทียบ SHA-256 ของทุก byte กับตัวสร้างเดิมและตรวจการแยกบัฟเฟอร์ การแก้ข้อมูล และการ dispose/recreate ส่วน browser ตรวจโมเดล 195 ชุดค่าต่อคุณภาพ high/low รวม 390 ชุดค่า ตรวจฉากที่ใช้พร้อมกันไม่ dispose ทรัพยากรข้ามกัน และ GPU geometry/textures เหลือศูนย์หลังปิดโมเดล รวมทั้งเปิดใหม่ได้ Build regression และ browser ที่ `/school/` ขนาด 390px ผ่าน Login, รูป, 3D และค่าทดลองหลัง reload โดยไม่พบข้อผิดพลาด รายงานโมเดลเก็บสำเนาที่ `tmp/performance-leaf-cache-20261025/model-browser-report.json`

รายงาน diagnostic: `tmp/performance-leaf-cache-20261025/startup-verified.json`; build, hash และ backend snapshot: `tmp/performance-leaf-cache-20261025/manifest.json` ชุดวัดตรวจ hash ตาม manifest ก่อนใช้ bytes และเก็บข้อมูลที่อ่านไว้ในหน่วยความจำตลอดการรัน บันทึกการรันที่ล้มเหลวแยกไว้ใน `startup.json` (ตัววัดเดิมยังไม่รองรับชื่อไฟล์ inline ของ build; แก้ตัววัดแล้ว ไม่ใช่ความผิดพลาดของเว็บ) ไม่มีการเผยแพร่หรือเรียกบัญชีจริงในงานต่อนี้

## ผลตรวจประกอบ

- Client/server/privacy 19 tests, bundler 5 tests และเครื่องมือวัด/สรุปผล 10 tests ผ่าน รวม **34 tests**
- Browser หน้าครู/แอดมินผ่าน desktop และมือถือ รวม API รุ่นเดิม, ค้นหา/ลองใหม่, ถอนสิทธิ์ และส่งผลของนักเรียน
- Build เปิดใต้ `/school/` ผ่านที่ 390px รวม Login, รูปบทเรียน, dynamic imports ของ 3D และค่าทดลองหลัง reload ไม่พบ page/network error
- ตรวจ deployment ของ build ใหม่ผ่าน: ลำดับ/เนื้อหา JavaScript, CSS และ URL รูป/ฟอนต์ถูกต้อง; HTML 2,381 bytes หรือ gzip 1,156 bytes

## รันซ้ำ

ใช้ Node ที่ติดตั้งไว้ หรือ executable ของชุดทดสอบใน workspace นี้:

```powershell
$testNode = '.\tmp\browser-check\playwright\driver\node.exe'
& $testNode scripts/prepare-performance.mjs tmp/performance-next
& $testNode tests/navigation-performance.mjs --manifest tmp/performance-next/manifest.json --samples 3 --output tmp/performance-next/controlled.json
& $testNode scripts/summarize-performance.mjs tmp/performance-next/controlled.json --output tmp/performance-next/summary
& $testNode tests/simulation-startup-profile.mjs --manifest tmp/performance-next/manifest.json --samples 3 --output tmp/performance-next/simulation-startup-profile.json
```

เลือกชื่อปลายทางใหม่ทุกครั้ง ตัวเตรียมเก็บ frontend ก่อน/หลังและสำเนา `Code.gs` แยกจากไฟล์ที่กำลังแก้ พร้อม SHA-256 ของ backend ชุดวัดตรวจ hash ก่อนเริ่มเพื่อไม่ให้ผลใช้ backend คนละรุ่นกับที่บันทึกไว้ ไฟล์ใต้ `tmp/` ไม่เข้า Git หรือ Pages

ตัววัด startup รองรับ `--manifest` เพื่อสลับวัด build ก่อน/หลัง; ถ้าไม่ใส่จะวัด workspace รุ่นเดียว ใช้ `--check` ตรวจจุดแทรกตัวจับเวลาและ hash โดยไม่เปิด browser และเลือก output ใหม่เพราะตัววัดปฏิเสธการเขียนทับรายงานเดิม สำหรับ snapshot ที่มี `frontendHashes` จะตรวจ hash ทุกไฟล์ที่ใช้ด้วย ตัวเตรียมปกติข้างต้นเทียบ HEAD กับ workspace ทั้งหมด; ตาราง cache ที่แยกผลเฉพาะผิวใบใช้ snapshot สองชุดที่เตรียมด้วย `tmp/performance-leaf-cache-20261025/prepare.mjs` และมีไฟล์อื่นเหมือนกันทั้งหมด

ชุดวัดมี timeout ของแต่ละขั้นตอน รวมถึงการ decode รูป บันทึกการล้มเหลวโดยปิดบังข้อมูลบัญชี และเก็บขั้นตอนที่ทำสำเร็จก่อนเกิดข้อผิดพลาดพร้อมสถานะ failed รายงานสรุปแยกแต่ละ input/backend เสมอ และป้องกันการเขียนทับไฟล์ผลดิบที่ป้อนเข้า
